Flow instance editor

Network automation

Role + Timeline

UX Designer + 1 year

Objective

The goal of this project was to present an appropriate solution where the operator is able to create an instance flow from the inventory page and then view the details of the flow to identify and diagnose errors that occur in the network service before an instance flow is completed. This software solution would work in tandem with other parts of the platform such as design studio and operational hub (where the network service infrastructure is planned, designed and built) which would increase efficiency and reduce costs for the business.

Problem statement

How might we increase network function efficiency by reducing downtime in identifying and resolving errors in flow instances? How might we design a solution that enables the operator to quickly view and diagnose errors when a network service instance is run? Currently the operator isn’t able to view error states until the instance lifecycle is completed and this presents problems of inefficiency in identifying and resolving errors, as well as increased workloads for the operator. This also creates problems for the businesses because their network services break down more frequently and this is cumbersome and expensive.

Design process

I began my design exploration by going broad and coming up with ideas based on feedback from technical experts and workshops with my team. I learned about the anatomy of a network service flow instance and made decisions on what information is necessary and how they should be displayed to the user and mapped out the user and task flows for the application. I generated a lot of ideas quickly to present to my team and talk through my design thinking for each element or component that includes. I made sure to tie this back to how it impacts the user and addresses their needs and pain points. I iterated continuously through multiple feedback cycles and began to narrow down my designs. When working towards an MVP, I keep in mind that there are trade-offs to be made for every design exploration while addressing potential build challenges and edge cases that might be encountered with users.

Multiple explorations

I explored multiple iterations of the details page and explored questions for specific tasks the user needs to complete to view and diagnose errors in the application.

    What are the aspects that emphasize read-only mode for the details view?
    What is the best way to view a workflow in read-only mode? How is this communicated to the user?
    What are the minimum and maximum steps to show in the workflow details?
    Should there be an automated way to draw the user’s attention to the failed tasks and sub-tasks?
    What information is important for the user to view to assess a failed task? For instance, properties, flow sequence, surrounding tasks, run time, conditional tasks, multiple pathways.

Challenges and constraints

One of the challenges of this project involved understanding the scope of the problem I was attempting to solve and the business purpose within the larger automation platform. I spent a lot of time meeting with product managers, technical experts and cross-platform client facing teams to understand who our users are, what the product or service is and how it fits within our business unit. There were numerous workshops to align on users, personas, journey mapping, task flows, and product integration. I led discussions on strategy on how to approach this project by focusing on what is important to our user and how to integrate our new offering with the rest of the platform. Time constraints and fitting this new product into the release schedule was also another factor.
